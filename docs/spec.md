# CTI Product Assistant — Spec

What the application is and what its parts are contracted to do. This is a
contract, not a sequence — see `docs/plan.md` for build order.

---

## Product

A public RAG chat application answering product and price questions over the
CTI price masterlist: 1,038 items of workplace safety, facility and
institutional equipment.

**User.** A sales staffer, dealer, or prospective customer asking "how much is
X", "what do you have under ₱Y", "what do I need for a construction site".

**Non-goal.** Not an ordering system, not an inventory system. It quotes list
prices and explains the catalog. Stock, lead time, discounts and delivery are
explicitly out of scope and must be refused, not estimated.

## Data

Source of truth is `corpus/`, generated by `scripts/build_corpus.py` from
`fixed-cti-masterlist.xlsx`. See `corpus/README.md` for record shape and
`docs/corpus-design-decisions.md` for why it is shaped that way.

**Storage — two mechanisms, deliberately:**

- **Upstash Vector** holds the vector index over the `text` field of each
  product chunk, plus the guide documents chunked by `##` heading. Hosted,
  serverless REST — no connection pooling inside a Vercel function, and the
  index survives restarts.
- **An in-memory array** backs `filterProducts` **and the exact-match half of
  hybrid search**. `products.json` is imported at module scope and filtered
  with plain JavaScript — no database call. The corpus is ~1 MB, static, and
  regenerated by a build script, so counts, sorts and range filters are exact
  and instant without query-language friction.

**Hybrid retrieval needs no keyword index.** Exact `code` and `name` matching
runs as a regex/string scan over the same in-memory array — 1,038 records is
instant. This removes the dependency on the vector store's full-text
capabilities entirely, which is why the store choice is free.

Chunks are atomic — one product each — and must not be re-chunked at ingest.

**Metadata carried on every product chunk:** `code`, `code_group`, `name`,
`category`, `department`, `price_php` (integer), `price_band`, `currency`,
`colors`, `attributes`, `source_row`, and `data_quality_flag` where present.

Guide chunks carry `doc_type: "guide"`, `title`, and the section heading.

## Tools

The model has exactly two retrieval tools. Tool descriptions must make the
boundary unambiguous — vague descriptions are a named failure mode in the
brief.

### `searchProducts`

Semantic and keyword search over product chunks and guide documents.

```ts
searchProducts({
  query: string,              // natural language or product code
  department?: string,        // optional narrowing
  limit?: number              // default 12, max 20
}) => Array<{
  code, name, category, department,
  price_php, price_band, colors, attributes,
  text, score, data_quality_flag?
}>
```

**Use for:** naming or describing a product, asking what something costs,
asking whether an item is carried, and any conceptual question about the
catalog, codes, or pricelist conventions.

**Behaviour.** Exact matches on `code` and `name` — found by scanning the
in-memory array, not by a second store query — are merged ahead of vector hits.
A query that looks like a product code (`/^[A-Z]{3}-\d{3}/i`) must return its
exact match first when one exists.

### `filterProducts`

Direct query against the in-memory product array. Not semantic, no database
call.

```ts
filterProducts({
  category?: string,
  department?: string,
  min_price?: number,
  max_price?: number,
  color?: string,
  oshc_only?: boolean,
  sort?: "price_asc" | "price_desc" | "name",
  limit?: number              // default 20, max 50
}) => {
  items: Array<{ code, name, category, price_php, ... }>,
  total_matching: number      // before limit — required for count answers
}
```

**Use for:** price thresholds ("under ₱500"), superlatives ("cheapest safety
shoe"), counts ("how many chairs"), and browsing a category.

**Why separate.** Vector search answers these confidently and wrongly — asked
for everything under ₱500 it returns `limit` arbitrary rows and presents them
as complete. `total_matching` exists so the model can say "23 items match,
here are the 20 cheapest" rather than implying it has listed them all.

## Retrieval configuration

| Parameter | Value | Rationale |
|---|---|---|
| topK | 12 (max 20) | Chunks are short and single-product; variant families need to return together |
| Chunk strategy | One product per chunk, no overlap | Overlap is meaningless for atomic records |
| Guide chunking | By `##` heading | Each chunk is a self-contained explanation |
| Hybrid merge | Exact code/name matches first, then vector by score | Codes are near-identical under embedding |

Tunable during M3. Any change made for a reason should be recorded in
`docs/corpus-design-decisions.md`, since retrieval tuning is reflection
material.

## System prompt contract

The model must:

1. Quote prices **only** from retrieved chunks. Never estimate, interpolate, or
   recall a price from general knowledge.
2. State the **product code** alongside every price.
3. Format prices as `₱43,470.00`, with thousands separators.
4. When several variants exist (sizes, capacities, chemical types), **list them
   with prices** rather than picking one.
5. When a retrieved chunk carries `data_quality_flag: "duplicate_code_conflict"`,
   **warn** that the masterlist holds conflicting entries for that code and
   refer the user to the sales team. Do not pick a price.
6. When retrieved items do not clearly match the question, **say so and ask for
   the product code** rather than answering from the closest match.
7. **Refuse and redirect** on stock availability, lead time, discounts,
   delivery cost, warranty, quality comparisons, and technical specs beyond the
   item name. These are documented in
   `corpus/guide/04-answering-price-questions.md`.
8. Mention **related items** where the catalog overview documents a buying
   pattern — a harness pairs with a lanyard, a welding mask with gloves and an
   apron.

## Interface

**Chat.** Streaming responses (R2). Tool calls visible while running, so the
user sees retrieval happening rather than a dead pause.

**Sources render as soon as retrieval completes, not when the answer does.** A
tool-calling turn runs tools first and generates text second, so the full
source set is known before the first token arrives. The panel populates at that
point and the answer streams in beside it — the user sees what is being
grounded on before reading the claim. Do not defer source rendering to message
completion; it discards information that is already available.

**Citations are panel-only. No inline `[1]` markers.** The brief requires
showing retrieved sources, not inline reference markers. Getting a model to
emit markers reliably is prompt-tuning effort with no rubric payoff, and the
source cards — code, name, category, price — already make the grounding
visible. Revisit only if M5 finishes early.

The starter satisfies this already: `useChat` exposes `toolInvocations`, and an
invocation reaches `state === 'result'` before the text part begins streaming.
Render sources off that state rather than off message completion.

Deferred to M5: how sources group when a turn calls both tools, and the
stop/abort control.

**Sources panel.** Every answer that used retrieval shows its sources as
product cards: code, name, category, price, colors. The displayed price renders
from the `price_php` metadata field — **never** parsed from model output. This
is what makes the shown number exact by construction.

Guide-document sources render differently from product sources: title and
section heading rather than a product card.

**Empty state (R6).** Not a blank box. States what the assistant covers, and
offers suggested-prompt chips drawn from the real catalog — one per question
type:

- "How much is MED-001-01?"
- "What fire extinguisher types do you carry in 10 lbs?"
- "What safety equipment do you have under ₱500?"
- "What do I need to outfit a construction site?"

**Mobile.** Usable at 375px. Sources panel collapses below the chat rather than
sitting beside it.

## Security

- All API keys server-side only, in route handlers. No key reaches the client
  bundle (R5).
- Env vars: named identically in `.env.local` and in Vercel project settings.
  Mismatched production env var names are a named failure mode in the brief.
- `.env.local` gitignored. Verified before first push.
- No user data persisted beyond the request.

---

## Out of scope

Authentication, rate limiting, conversation persistence, multi-turn memory
beyond the current thread, ordering or quotation generation, image display,
admin editing of the corpus.

Stretch goals are capped at two by the brief. Committed: **hybrid retrieval**
(required by the corpus shape, already specified above) and **suggested-prompt
chips** (doubles as the empty state). Anything else is out.
